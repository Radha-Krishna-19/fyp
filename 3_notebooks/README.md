# Analysis notebooks

Two notebooks. They run the **identical** pipeline — same bonding rule, same
supercell rule, same influential-node selection, same τ definition, same q grid.
The only difference is where the structures come from. That is deliberate: if
the two differed in any analysis step, comparing their outputs would be
meaningless.

| Notebook | Structures | Output | Status |
|---|---|---|---|
| `mof_band_analysis.ipynb` | 77 hMOF frameworks — hypothetical, computer-generated | `results.json` | Run; produced the band |
| `real_mof_band.ipynb` | CoRE MOF 2019 — experimentally synthesised | `real_results.json` | **Run — 61 frameworks** |

---

## Why there are two

Everything quantitative in this project was computed on **hMOF** structures:
chemically sound, assembled from real building blocks under real bonding rules,
but generated by a program and never made in a laboratory.

That was not the intention. The original notebook asked MOFX-DB for
`CoREMOF 2019` and received hMOF records instead.

**The cause.** On that endpoint the `database=` parameter is advisory. When it
is supplied together with a `gases[]` filter, the gas filter wins and the
database filter is silently ignored. The request was correct; the response did
not honour it. Nothing errored — the run simply analysed the wrong class of
material and reported it as though it were the right one.

**How we caught it.** A provenance check further down the notebook compares the
`database` field of each returned record against what was asked for, and prints
a warning on a mismatch. That check is the only reason this was found rather
than published.

**The fix**, now in both notebooks: filter every returned record on its own
`database` field and discard anything that is not CoRE MOF, instead of trusting
the server-side parameter. Asking politely is not a provenance guarantee;
checking each record is.

## Running `real_mof_band.ipynb`

Open it in Google Colab. It installs its own dependencies.

1. **Step 2** streams MOFX-DB and keeps only verified CoRE MOF records. It
   prints how many were streamed, how many kept, and what was discarded, then
   asserts that nothing unverified survived.
2. If the API is unreachable, set `USE_LIVE_QUERY = False` and put `.cif` files
   in `real_cifs/` instead. The rest of the notebook is unchanged.
3. **Step 12** compares the result against the 77-framework band. Upload
   `results.json` from this folder alongside the notebook to enable it — without
   that file the cell still reports the real band on its own.
4. **Step 13** bundles everything into `real_mof_results.zip` and downloads it.

**Runtime:** roughly 15–25 minutes for 50 frameworks on a free Colab CPU. The
expensive step is the all-pairs shortest-path computation on each supercell,
which is `O(N²)` in memory.

### Send back

`real_results.json` — that is the file the website reads. The figures in the zip
are useful too but are regenerated from the JSON anyway.

---

## What Step 12 checks before it reports anything

Δα rises with graph size, so comparing two sets of different sizes measures the
size difference rather than the chemistry. This is not hypothetical: it is
exactly the confound that forced us to withdraw the pore-size claim from the
77-framework analysis.

So Step 12 reports, in this order:

1. the block-count range of each set,
2. whether those ranges **overlap** at all,
3. the Δα ranges restricted to the overlapping sizes,
4. the correlation between Δα and block count *within* each set.

If the block counts do not overlap, it says so and tells you not to claim a gap.
A separation that only exists between size-mismatched sets is not a finding.

## Current state of the comparison

61 synthesised frameworks from CoRE MOF 2019 have been through the pipeline,
expanded under the same 48 Å rule. Spectra in `real_results.json`.

| Set | n | Δα | mean | mean asymmetry |
|---|---|---|---|---|
| Hypothetical (hMOF) | 77 | 1.02 – 1.41 | 1.180 ± 0.095 | −1.31 |
| Synthesised (CoRE MOF) | 61 | 0.95 – 1.47 | 1.198 ± 0.132 | −1.31 |

The ranges overlap over 1.02–1.41, covering 82% of the synthesised set and 100%
of the hypothetical one. Means differ by 0.018 (Welch *p* = 0.38, Mann–Whitney
*p* = 0.39, Cohen's *d* = 0.16). One difference is real: the synthesised set is
significantly more variable (Levene *p* = 0.010) — frameworks people actually
made are more structurally varied than frameworks one algorithm generated.

**Withdrawn.** An earlier version of this table reported 4 synthesised
structures at Δα = 1.66 – 2.26 with "no overlap, and a gap of 0.25". Those four
were 256–972 atoms against the hMOFs' 3024–6592, and Δα correlates with **atom**
count at r = +0.73 (the r = +0.11 previously quoted is against **block** count —
a different quantity, and the wrong one to check a size confound with). The gap
was a size artefact.

Both readings, and which one the data chose, are set out on the Results page of
the project site.

## A portability note on these JSON files

`results.json` and `real_results.json` contain bare `NaN` tokens. Python's
`json.dump` writes them and `json.load` reads them back, so the notebooks never
notice — but **`NaN` is not valid JSON**, and any other reader (JavaScript,
`jq`, most strict parsers) will reject the file outright.

The NaN sits in the `r2` array at q = 0. There, τ is fitted through the origin
against a flat line, so R² is genuinely undefined rather than merely missing.
Anything consuming these files from outside Python should substitute `null`:

```js
JSON.parse(fs.readFileSync(p, 'utf8').replace(/\bNaN\b/g, 'null'))
```

`1_website/tests/test_real_band_numbers.js` does exactly this. The files are
left as-is rather than rewritten, because they are the notebooks' own output
and regenerating them to change a serialisation detail would break the claim
that nothing between the run and the site is hand-edited.
